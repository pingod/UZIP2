# UZIP2
解压缩小工具，支持自动尝试指定密码。
# 项目由来
最近下载资料多些，解压逐个输入密码过于麻烦，想找个右键菜单一键解压的软件，在网上发现了UZIP2项目，作者是farkaway，应该是放弃维护了，两年没更新了。farkaway在[网站](https://www.yuque.com/farkaway/uzip/gggnsn#l3PpV)上提供了2.22版本和项目源码。我在2.22版本上，根据自己需求做了进一步定制。因该项目在网上无代码托管，并且联系不到作者farkaway，所以修改后的代码无法回流到作者farkaway，故此，我开了本仓库。

# 我的修改

1. 对剪切板导入的密码去重。
2. 程序支持命令行和右键菜单调用，并支持多个文件解压。
3. 优化代码格式，如制表符改成空格，删除多余引用，格式化代码等。
4. 优化临时缓存文件夹相关代码，每个压缩包有单独的缓存文件夹，并且该文件夹是隐藏的。
5. 支持多级解压，压缩包内第一层压缩包再次解压，持续符合条件时会循环解压。

## 本次增强（v3.8 — 悬浮方块进度环 + 审计第二轮：更新链路 / CLI 补漏 / 性能）

v3.7 交付后又把整条更新链路、CLI 剩余死参数和几处热路径过了一遍，外加一个可见的新功能：桌面迷你方块的**进度环**。仍按"先写会失败的定向测试 → 最小实现"推进，测试从 642 个增加到 **763 个**（新增 121；新测试文件 `PuckProgressTests` 23、`UpdateTransportTests` 22、`PuckHintTests` 10、`PuckPlacementTests` 6、`CoalescerTests` 4，另有 `SevenZipCoverModeTests` 11、`SevenZipProbeEarlyExitTests` 8 补在既有文件里），全绿；主工程与测试工程 Debug/Release 均 **0 警告、0 错误**。

**新功能：进度环**

1. **悬浮方块外圈进度环**（`PuckProgress` + `MiniPuckWindow`）：图标外那圈描边就是进度，**转完完整一圈 = 100%**，从 12 点起顺时针。多个任务同时跑时画的是整批平均进度；批内最后一个任务收尾后，环补满一整圈停 2 秒再收起——"跑完了"这件事不需要盯着主页也能看见。提示位与环共用一次判定（新增纯函数 `ResolveHint`）：预览 > 完成 > 进度 > 空闲，所以闪示一结束文案自动回到"拖到这里"，而不是永远卡在"完成"上——这条正是真机冒烟看图看出来的缺陷。文件正拖到方块上方时不抢提示位（那里显示的是包内预览）。几何计算全部是纯函数：`SweepAngle(percent)`、`Overall(jobs)`、`RingGeometry(percent, size, thickness)`，越界/null 归零，满圈用两段 180° 弧闭合（WPF 的 `ArcSegment` 没有扫掠角属性，360° 单弧会直接消失，这是实测出来的）。进度值来自解压线程，直接刷 UI 一个包就是几百次重绘，所以只置脏、由 200ms 心跳统一重画，并只订阅活跃作业。

**缺陷（更新链路与 CLI）**

1. **P0：自更新的版本闸门从 v3.3 起就是死的**。`Verify` 拿四段文件版本（`3.7.0.0`）去逐字符比 tag 派生的期望值（`v3.7`→`3.7`），只要 tag 写成两段——我们历来的发布 tag 都是两段——就地更新永远"版本不一致"被拒。改成按段比较（前 3 段，忽略尾部 revision），并给一个用真实 `_rel` 产物跑通 `Verify` 的用例把这条路径钉住。
2. **代理侧被限流 = 更新彻底不可用**：本机实测 GitHub API 走代理返回 403（限流）、直连 200，旧实现只试一次。现在传输层按 curl 的语义工作——`HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` 分协议，值写 `direct` 或主机命中 `NO_PROXY` 就是明确不走代理；遇到传输类失败（`HttpRequestException`/超时/`IOException`/`SocketException`）自动降级重试一次直连，元数据、`.sha256` 侧车、exe 下载三条路共用这一套。测试用注入的 transport 断言"恰好一次调用"或"先代理后直连"的确切序列。
3. **`--cover` 是参数注入口**：它原样拼进 7z 命令行，而 `settings.json` 用户可编辑，写 `-aoa -y -r C:\` 之类的东西会一路带到进程参数里。现在 CLI 解析层与 `SevenZipClient` 收敛点各校验一次，只放行 7z 真实存在的四个覆盖模式（`-aoa`/`-aos`/`-aou`/`-aot`），其余退出码 2；两层都测。
4. **`update --check` 是个死参数**：文档写着"默认等价 `--check`"，代码里没有这个分支。补上（`--check` 只报告版本信息），并拒绝它与 `--apply` 同时给——一个是"看看"，一个是"真换身体"，一起给没有意义。
5. **方块记不住副屏**：`MiniPuck` 的位置恢复按 `SystemParameters.WorkArea`（只有主屏）夹坐标，于是"把方块拖到副屏"这件事一重启就被拽回主屏右下角——本机实况：用户存下的 `puckLeft=2624, puckTop=1421` 每次都被夹成 `2456,1288`。改为按整个虚拟桌面夹（新增纯函数 `PuckPlacement.Resolve`），负值仍是"从没放过"的哨兵，越界则整块拉回可见范围。

**性能**

6. **加密探测该跳就跳**：手里一条候选口令都没有（没手动输、文件名里没有、密码本/密码纸/外链都空）时，`ProbeEncryptionAsync` 的结论没有任何下游用途，跳过它。64 KB 包实测探测 11.4–16.7 ms、解压 11.7–13.1 ms——对小包这等于砍掉近一半的固定开销。顺带确认跳过之后加密包的诊断文案不但没变差反而更准（原先空口令那趟会把"需要密码"说成"文件已损坏或不是可识别的压缩包"），这一点也写成用例。
7. **加密探测提前收刀**：探测只需要第一条 `Encrypted = ` 行，旧实现却让 7z 把整包列完、把几千条目的 stdout 全读进缓冲（2000 条实测约 328 KB）。现在在输出回调里认出该行就当场结束进程。
8. **主线程/队列上的重复劳动**：主页三个计数（失败/完成/活动）是按钮可用性与横幅的唯一数据源，原先每个作业状态一变就整表扫一遍，200 张卡片连着收尾就是 200 次全表扫描——改为合并到一次排队（新增 `Coalescer`，`Interlocked` 单字标志，64 线程并发只放行一次的用例）。7z 进度行解析换成 `[GeneratedRegex]`；`DebugMode` 关掉时不再构造脱敏命令行字符串。
9. **长列表虚拟化**：主页与历史页原先是"外层 `ScrollViewer` + 裸 `ItemsControl`"，这个组合天生不虚拟化，几百张卡片全部实例化。改成 `VirtualizingStackPanel` + `Recycling` + 控件自带 `ScrollViewer` 模板（外层再套一个 ScrollViewer 就会把虚拟化整个废掉，这是这轮踩到的 WPF 事实）。

**打包 / 元数据**

10. **`scripts/publish.ps1` 产出直接可上传的文件名**：框架依赖主产物从 `UZIP-<版本>-win-x64.exe` 改为 `UZIP2.exe`（连同 `UZIP2.exe.sha256`），与 `UpdateService.PickAsset` 认的名字一致——以前发布时要手工改名，改一次就容易漏改侧车，校验和直接对不上。发布构建的 verbosity 从 `-v q` 提到 `-v m`，警告会打在发布日志里而不是被吞掉。
11. **程序集元数据不再是从前那台机器的模板**：公司/版权还是 `HP Inc. / 2021`，换成仓库署名与 2021-2026，描述补上"UZIP2 现代压缩包工具（7-Zip 前端）"，版本同步 3.8.0.0。
12. **`release/` 里的 .NET Framework 残留删掉**：`App.config`/`UZIP2.dll.config` 声明的是 `.NETFramework,v4.8` 运行时，而 CI 把整个 `release/` 目录当产物上传——一份和 .NET 8 单文件无关的东西跟着发布件走。删除后 `install.ps1`（缺文件就不拷）与 `uninstall.ps1`（有才删）的既有容错路径照旧成立。

**刻意不做的几件事**（评估过、成本收益不划算，留在这里以免被当成遗漏）：更新检查的 ETag/条件 GET 与 TTL 缓存（每天一次的固定成本，不值得引入缓存正确性风险）；watcher 的 `Changed` 去重与"启动先扫一遍现存文件"；跨进程的历史/设置写回合并（后写者覆盖，已在已知限制里）；InstanceBus 转发缺少 ack 与日志；历史搜索输入的防抖；重定向 CLI stdout 的 UTF-8 代码页设置。

**真机冒烟补做了什么**：单测进程里没有 WPF 消息泵，进度环这类"看得见"的东西只能拿真二进制跑一遍。做法是在 `artifacts\smoke\run` 起一个带独立 `Config` 的隔离实例（不碰部署版的数据），把方块放到副屏（`puckLeft=2700`），再用第二个进程把包通过单实例管道转给它——等价于把文件拖上方块——期间按 1.2 秒连拍方块窗口的真实矩形。为了不把"环有没有长大"交给肉眼，连拍里对每张图统计强调色像素数：空闲基线 180（外框与图标本身是强调色），满环再加约 170。解一个 4GB 的 solid 7z 读到的序列是 `180 → 180 → 180 → 210 → 246 → 268 → 310 → 350 → 350 → 180`，中间帧截图上是约四分之三圈配"75%"，收尾满环配"完成"，两秒后环收起、文案回到"拖到这里"。这轮冒烟同时抓出并修掉了两个单测原理上盖不住的问题：方块记不住副屏（缺陷 5）与闪示后提示位回不来（新功能 1）。**仍未真机验证**：主页/历史列表虚拟化的滚动手感（只有编译与静态检查）。

## 历史增强（v3.7 — 全量审计：并发缺陷清账 + 性能 + 格式互转/包对比）

对 v3.6 做了一轮完整体检：并发与资源缺陷、CLI 正确性、服务层健壮性、性能、还能加什么场景，逐项按"先写会失败的定向测试 → 最小实现"推进。修掉审计发现的 14 项缺陷（P0 5 项 / P1 9 项；下面按主题重排展示，其中有 4 项属必死锁或必崩级），做了 6 项性能优化，新增 5 项功能。

**缺陷（会丢数据、死锁或崩进程的那一批）**

1. **密码本死锁**：`Changed` 事件原先在持有 `_sync` 的回调里派发，订阅者（主页/设置页）回头读 `Book`/`Paper` 就在等自己手里的锁——必死。改为锁外派发，并明确"调用方必须持有 `_sync`"的注释契约。
2. **取消永远取消不掉**：`CancelJob` 的"读状态"和"找 cts"分两次加锁，派发循环恰好在这中间把 Queued 翻成 Running，刚打的 `CancelRequested` 标记就没人再看。现在判定与 cts 查找同锁原子完成；重试同理，否则会在"刚终态、尚未收尾"的窗口里重复入队。
3. **临时目录泄漏**：session temp 建在解压输出目录（往往是用户下载盘），而回收只扫程序目录。现在创建时在 `Config\` 记一笔账，启动按账逐条回收，并且"中途失败/取消/抛异常"都保证 `TryDeleteTemp` 走 finally。
4. **半截压缩产物**：`7z a` 边压边写，取消或失败会留下头部完整、数据不实的档案，用户下次双击只得到"文件已损坏"。现在当场删掉（分卷按 `.001/.002…` 顺序删到第一个缺口），自检也提前到删源文件之前——坏包不能等源没了才暴露。
5. **文件过滤硬删**：过滤掉的条目无视"删除到回收站"设置直接 `File.Delete`。已跟随该设置。
6. **分卷假成功**：同批影子作业原先凭空报绿。现在按"主卷认领"模型把主卷的真实终态回灌给影子作业，主卷失败我也失败。
7. **UI 线程一崩带走全程序**：新增 `CrashGuard`，UI 线程非致命异常记日志+提示后继续跑，后台线程崩之前先把现场写进日志，未 await 的 Task 不再静默吞掉；OOM/栈溢出这类致命异常照旧放行（在坏状态上继续写用户文件更危险）。
8. **监听目录静默停摆**：`FileSystemWatcher.Error`（缓冲溢出/目录被删）在 .NET 里只会抛到线程池——不接住就是整个进程崩，接住不重建则 UI 仍显示"监听中"。现在接住并按当前设置重建 watcher。

**缺陷（P1）**：`AtomicFile` 固定 `.tmp` 名导致 GUI/CLI 两个进程互相搬走对方的临时文件（改为唯一临时名）；历史页"重跑"丢掉当时成功的口令，把本来成功的作业重跑成必然失败（校验类记录也不再按解压语义重跑）；一批 20 个档案解到同一目录弹 20 个资源管理器窗口（按批去重，且路径大小写/尾分隔符不同不算两个目录）；`--json` 输出泄露明文口令（默认脱敏，`--show-passwords` 才显示）；CLI 命令词/选项拼错被静默忽略（现在退出码 2 报错）；`-o ""` 这类显式空值被吞掉后顺走下一个参数；7z 的 stderr 未设 UTF-8 导致中文包名乱码、错误分类跟着失效；`7z t` 的判据只看 "Everything is Ok" 文案（现在以退出码为准，认不出关键字时按官方退出码兜底）；等等。

**性能**：加密包解压从"每条口令先全量 `t` 一遍、命中再 `x` 一遍"改成"候选口令直接解进私有 temp，错了清空再试"——命中那条只读一遍盘，清单已确认加密的包连空口令那遍都省；并行名额从 20 ms 轮询改成 `SlotPool`（等待者挂 `TaskCompletionSource`，作业收尾或并行度调大当场唤醒，且不再有"两线程同时认为还剩一个名额"的超发）；历史写盘节流合并（退出/CLI 收尾前 `Flush`）；外链密码整批复用（独立锁，网络 I/O 绝不攥着密码本）；失败气泡加最长等待期兜底，监听目录不停喂作业时不再永远不播报。

**新功能**

1. **格式互转**（GUI 卡片「转格式」+ 工具条「转为」下拉，CLI `convert`）：解包后按目标格式重打包，走的是 GUI 同一套流水线，所以密码链、压缩后自检、历史落库与主页行为一致。**原包一律保留**——重打包会丢包内元数据，而转换最常见的失败恰是解不开源包，删源就是双重损失。目标格式表收敛到新的 `ArchiveFormat`（`-t` 开关名与文件后缀是两张表：实测 26.03 里 `-tbz2`/`-tgz` 会报错，必须是 `bzip2`/`gzip`）。`bz2/gz/xz` 是单流格式只装得下一个文件，这句由程序讲清楚而不是丢给 7z 的英文 `Sub items data error`。复合后缀会一路剥净（`a.tar.gz → a.7z`），撞名自动 `-New1`。
2. **包对比 diff**：`ArchiveDiff` 纯函数比较两个包的清单（不读文件内容），退出码沿用 GNU diff 约定（0=一致、1=有差异），脚本里可直接判分支；zip 存 `a/b`、7z 存 `a\b` 且 Windows 不分大小写，键必须先归一，否则满屏假差异。预览窗口新增「对比另一个包」按钮，就地看差异清单并返回。
3. **右键"解压并预览"**：注册表多一项，单个包先出包内清单让用户勾选再解；多选无从预览，照常直接入队。因为注册项从 5 个变 6 个，旧注册会被识别为过期并提示重新注册。
4. **压缩后校验产物**（设置里默认开启，CLI `--test/--no-test`）：压完先 `7z t` 自检，产物坏了当场报，而不是等下次解压才发现；校验不过不删源文件。
5. **更新包 SHA-256 核对**：`scripts/publish.ps1` 为每个产物产出 `<产物>.sha256` 侧车（sha256sum 格式），应用内自更新下载后核对它——发布了侧车就必须核对，取不到摘要宁可不换。老版本没侧车时跳过这一步，不挡更新。

**刻意不做的两件事**：WinRAR 的 `-rr` 恢复记录在 7-Zip 26.03 里根本不存在（实测拒绝该开关），不做假开关；ISO 只能读不能写（`7z i` 里 Iso/Udf 都没有创建标志，实测 `-tiso` 返回"System ERROR: 未实现"），所以 ISO 不是转换目标，选它会得到一句明说"只能读取"的退出码 2，而不是一个名字叫 `.iso` 的 zip。相应地，认不出的 `--type`/`--name` 后缀不再静默降级成 zip。

## 历史增强（v3.3 — 一键自更新）

给程序加了自己升级自己的能力，不用再去发布页手动下、手动替换。参考了 Long 解压(Tauri 自动更新)的思路，但落到本项目的 WinExe + GitHub Releases 现实上：

1. **就地换体**：`SelfUpdater` 从最新 Release 挑出名为 `UZIP2.exe` 的框架依赖单文件直链，下载到当前目录的 `UZIP2.exe.update.new` → 校验 → 生成一个中继 `cmd` → **脱离启动**它 → 本进程退出。中继脚本等我们的 PID 消失后，用重试循环把新体覆盖到旧 exe（运行中的 exe 在 Windows 上会短暂锁文件，所以最多重试 8 次），成功后拉起新版、删掉临时体和脚本自身，最后删掉脚本自己。整个过程不碰 `Config`、`7-Zip`、`Bandizip` 等同目录数据。
2. **只在能安全换体时才就地更新**：`CanApplyInPlace` 拒绝三类情况——文件 >40MB（那是自包含版，拿 8.5MB 框架依赖直链去覆盖会把"免装运行时"变成"必须装 .NET 8"）、单文件解压缓存路径（`%TEMP%\.net\UZIP2\…`）、路径不存在或不合法。命中拒绝就回落到"打开发布页"，绝不硬来。
3. **版本必须精确匹配**：`Verify` 先查 `MZ` 头，再用 `FileVersionInfo` 读取版本资源，与目标版本逐段比对（`3.3.0.0`↔`3.3.0`），不一致就拒绝、删除临时体。下载体积另有 64MB 上限兜底，防止直链被换成别的东西。校验或下载失败/取消都会清理 `.update.new`。
4. **两个入口**：命令行 `update`（默认等价 `--check`，`--json` 带 `downloadUrl`/`size`/`canApply`）与 `update --apply`（下载→校验→就位后退出）；GUI 主页顶部"可更新"横幅在可就地更新时多出一个**一键更新**按钮（`CanAutoUpdate` 把关），点击后原地显示下载百分比，就绪即自动重启到新版。设置→关于的"检查更新"仍复用同一套逻辑，查到新版后主页横幅即出现按钮。
5. **代理与静默**：下载与检查更新共用 `UpdateService.NewClient` 的同一套环境代理策略（优先 `HTTP(S)_PROXY`，其次系统代理）；离线/被限流一律静默，绝不影响解压。

2. **覆盖全部功能**：
   - `list` / `test` / `extract`：列出、校验、解压，支持 `-o DIR` / `--here`（解到包所在目录）、`--password` / `--auto`（自动试密码本与密码纸）、`--entries a;b`（只解指定项）、`--cover -aoa`。

   - `shell`：`register`/`unregister`/`status` 管理 HKCU 右键菜单。
   - `watch once <目录>`、`update`、`help`、`version`。
3. **退出码**：`0` 成功 / `1` 操作失败（如错误密码、包损坏）/ `2` 用法错误。`--json` 给结构化输出，便于脚本消费。

5. **WinExe 等待注意**：主程序是 GUI 子系统（`WinExe`）。用 `AttachConsole` 接管父控制台，所以在 Git Bash / 交互终端里能直接看到输出并正常拿到退出码；但若从 cmd/PowerShell 脚本调用且需要**阻塞等待**，请用 `start "" /wait UZIP2.exe ...` 或 `Start-Process UZIP2.exe -ArgumentList ... -Wait`（详见 `UZIP2.exe help`）。
6. **无窗口挂死修复**：早期版本 `OnStartup` 里调 `Application.Shutdown()` 结束 CLI，但本工程 `ShutdownMode=OnExplicitShutdown` 且无窗口，dispatcher 循环尚未开始，导致进程挂住不退出——改为跑完 `Environment.Exit(code)` 直接终止；并把 headless 作业放到线程池上 `await`，避开 WPF UI 线程 `SynchronizationContext` 在 dispatcher 未泵消息时的经典死锁。

# [UZIP简介](https://www.yuque.com/farkaway/uzip/gggnsn)
UZIP是一个主要用于解压各种压缩档案的小工具，希望它可以为您提供更便利的解压功能。

有别于市面上其他压缩工具，其有以下主要功能特点：
1. 拖拽压缩/拖拽解压。所有的操作通过更直观的拖拽操作完成。

2. 密码管理功能。提供两种密码管理方式：密码本和密码纸，分别对应永久密码和一次性密码。您可以方便的贴入密码，以便在您需要的时候进行解压。

3. 批量测试解压密码。程序在您的密码本和密码纸中查找密码，并自动执行解压。

4. 解压文件过滤。过滤文件中的某些广告推广文件，避免手动删除的困扰。

5. 压缩日志。记录您压缩过的文件位置和解压密码，方便您随时找回。

6. 随机压缩密码生成。确保您每一个压缩文件都有不一样的密码。

7. 任意格式解压。即使文件后缀不是压缩格式，只需要勾选尝试解压位置格式（仅解压模式），就可以直接解压。

8. 从文件名中提取密码。只需要设定分隔标识符，程序就可以从文件名中自动提取解压密码。

9. 将解压密码写到文件名。您压缩的文件的文件名会包含密码信息，即防止在线解压，又避免遗忘密码。


### 运行环境


10. 程序基于 Microsoft .NET Framework 4.5，界面基于WPF 。 

11. WinXP系统应该无法使用，Win10 亲测可用，Win7，Win8未测试（理论可行）。

12. 程序基于cmd.exe命令行调用7z.exe实现解压/压缩功能。部分限制cmd命令行使用的设备无法使用。

### 使用场景

1. 只在固定的网站活动，只使用几个固定的解压密码。
在密码管理器 - 密码本中，填入这些密码，实现永久免密解压。
2. 出没于各个资源论坛，需要和各种各样的密码打交道。
    ○ 复制密码到剪切板，点击密码纸按钮，一键贴入剪切板内的密码到程序。
    ○ 选中密码，使用热键快速贴入程序。
3. 手机或其他设备无法使用程序。
尝试使用，从文件名提取密码。
4. 常常需要压缩文件，但经常忘记压缩密码。
在设置面板中，点击查看压缩日志按钮。输出位置、解压密码都可以找到。
5. 发布资源需要不同的密码。
在设置面板 - 压缩中，选择随机密码。
6. 下载资源里有很多奇奇怪怪的推广文件，找到需要的东西很费劲。
在设置面板 - 解压中，配置文件过滤选项。

### 使用说明

1. 程序基于7Zip 命令行方式进行解压/压缩。您可以通过设置，使用您自己安装的7zip.exe让程序工作。为了方便压缩包内置了32位的7Zip程序文件，可以自行替换为64位版本。
2. 程序做的事仅仅是替你输入命令行让7z工作，然后做一些7z没有做得事情。综合效率没有直接使用7z快，但使用上更方便了，省去了很多记录、查找解压密码的时间。
3. 理论来讲，7z.exe支持的所有格式都可以解压。但由于命令行限制，某些功能可能无法实现。
4. 解压\压缩时没有进度条，文件较大需要耐心等待。但，如果拖入多个文件可以看到文件进度。
5. 要注意，为了实现某些功能，程序会将压缩档案内的文件先解压到输出目录的UZipTempFolder文件夹内，再进行重命名，因此不要误删。
6. 作者是C#萌新，程序难免出现不可预料状况，如给您带来损失请见谅。
